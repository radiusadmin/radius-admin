A secure web console for FreeRADIUS.

radius-admin turns a FreeRADIUS 3.2 server into a network access control service you run from the browser. 802.1X, MAB, RadSec and switch logins live in one audited, role-based, MFA-protected portal, instead of hand-edited configuration files and SQL tables.

Every change is validated before FreeRADIUS sees it, and rolled back automatically if FreeRADIUS does not come back up.

Install steps View the code on GitHub

Runs on Ubuntu 24.04 LTS with FreeRADIUS 3.2.10, PostgreSQL 16 and nginx. No pip, no npm.

You always know whether a change is live

FreeRADIUS reads access decisions straight from PostgreSQL, so most edits need no restart. The few that do are held back until you apply them. The console uses one colour for each, and so does this page.

Live

Takes effect on the next authentication

  • Access rules: directory group to VLAN
  • MAB devices and approvals from the unknown-device queue
  • Switch administrator accounts
  • Settings

No restart. A rule tester shows which rule would match before a device ever tries.

Staged

Waits until you click Apply

  • RADIUS clients (switches, access points, controllers)
  • RadSec listener and per-client transport
  • Custom unlang policy

You review the difference, validate, then apply. Applying restarts FreeRADIUS through the safe-apply sequence above.

What you can run with it

One server, several kinds of client. Each row is a setup the project covers today.

Computers with certificates
Wired and wireless 802.1X with EAP-TLS. The computer's Active Directory group decides the VLAN, per wired port or per SSID. Nested groups work.
People and devices with a password
EAP-TTLS with PAP inside, for local accounts with groups and expiry or for Active Directory accounts, using the same access rules. PEAP-MSCHAPv2 where devices need it.
Printers, cameras and IoT
MAC Authentication Bypass with a VLAN per device, optional expiry and vendor names. Unknown devices that try to connect show up in a queue for one-click approval.
Switch and device administrators
Logins over RADIUS (PAP), limited to the management subnet, with optional privilege level 15.
Access points across untrusted networks
RadSec (RADIUS over TLS) per client. Move an access point to RadSec while your switches stay on plain RADIUS.
Regulated environments
Optional FIPS mode, a hash-chained audit log of every administrative action, and printable audit reports.
Teams with an identity provider
Admins sign in to the console with SAML single sign-on (Microsoft Entra ID tested). Their role comes from group membership.

Access rules you can test before anyone connects

The first rule whose group matches assigns the VLAN. No match means reject. FreeRADIUS reads the rules on every authentication, so a saved change applies to the next one.

The tester asks the same database function FreeRADIUS uses, and changes nothing.

A reason for every reject

The authentication log records every accept and reject. Open one and you get the reject reason, the client certificate, the directory groups and the access rule that matched, or the fact that none did.

Passwords are never stored.

Review the difference, then apply

Changes to RADIUS clients and the custom policy are rendered into two FreeRADIUS files. The Apply page shows exactly what would change, with shared secrets masked.

Validate runs the check without installing anything. Admins can roll back to an earlier backup from the same page.

A dashboard that says what is left to do

After the install, a setup checklist tracks what is still to configure: RADIUS clients, access rules, the switch-admin subnet and a first apply. Single sign-on, RadSec, switch monitoring and alert e-mail are optional steps.

Day to day it shows whether FreeRADIUS is running, whether the configuration is in sync, and the most recent rejects.

Everything it does today

Network access

  • RADIUS clients with per-client Message-Authenticator and Proxy-State settings (BlastRADIUS mitigations), generated shared secrets and CSV import.
  • RadSec per client: TLS 1.2/1.3, certificates from your CA, an optional expected certificate name, and OCSP revocation checks.
  • Access rules for wired or per-SSID connections, with a rule tester.
  • MAB devices and the unknown-device approval queue.
  • Switch administrator accounts, PBKDF2-hashed.
  • Custom unlang policy for administrators, checked before it is installed.

Operations

  • Dashboard, live sessions and change of authorization: disconnect, re-authenticate, bounce port.
  • Authentication log with the reason for every reject, the certificate, groups and matched rule.
  • SNMPv3 switch monitoring with per-port 802.1X state.
  • Alerts by syslog and e-mail: reject spikes, switches down, RADIUS down, portal down.
  • Audit reports as CSV or for print and PDF.
  • Safe apply with automatic roll back.

Console security

  • Local accounts with mandatory MFA (TOTP or client certificate) and three roles: viewer, operator, admin.
  • Step-up re-authentication for sensitive actions, and account lockout.
  • SAML single sign-on with group-to-role mapping, plus local break-glass administrators.
  • Hash-chained, append-only audit log.
  • Strict Content Security Policy. Light, dark or system colour theme.

Updates

  • An Updates page shows the installed and latest version and the changelog in between, and installs with a click.
  • Database backup first, health checks after, automatic roll back.
  • Choose a channel (main for stable releases, testing, dev), notify-only or automatic updates, and a maintenance window for updates that restart FreeRADIUS.
  • Builds are signed in CI with ECDSA P-384. The server verifies the signature before installing.

Why you can put it in front of network access

A console that controls who gets on the network is a target. These are the design rules the code is held to.

  1. Only the root helper is privileged

    The web application never runs as root, never writes FreeRADIUS files and never restarts a service. It stages files and asks the helper, which checks them against an allow-list before radiusd -XC ever runs.

  2. Request data reaches SQL only as hex

    Values from a RADIUS request, such as a user name or MAC address, are hex-encoded by FreeRADIUS and decoded inside database functions. They are never interpolated into SQL text.

  3. MFA is mandatory

    Local accounts need TOTP or a client certificate. Sensitive actions ask for re-authentication, and repeated failures lock the account.

  4. Every admin action is audited

    The audit log is append-only and hash-chained with SHA-256, so a removed or altered entry breaks the chain.

  5. Updates are signed

    Builds are signed in CI with ECDSA P-384. The root helper verifies the signature before anything is installed, and a failed health check rolls the update back.

  6. A small, closed surface

    The firewall admits port 443 only from the management subnet. PostgreSQL uses peer authentication with no passwords. Dependencies are distribution packages only, and the Content Security Policy allows no inline scripts or styles.

FIPS mode is optional

The cryptography is the same in both modes: SHA-2, AES, PBKDF2-HMAC-SHA256, ECDSA and TLS 1.2 or later. One FreeRADIUS build works in standard and FIPS mode. With Ubuntu Pro FIPS and FIPS mode on, the portal refuses to start unless the kernel and OpenSSL are in FIPS mode.

What it does not fix

  • The RADIUS protocol itself uses MD5. Per-client Message-Authenticator and RadSec reduce the exposure; plain RADIUS should stay on networks you control.
  • MAB is identification, not authentication. A MAC address can be copied, so give MAB devices only the access they need.
  • PEAP-MSCHAPv2 needs an NT hash of the password, so it is weaker. Local users have to opt in, and it is never available in FIPS mode.

The full account, including the cryptographic boundary and documented exceptions, is in docs/SECURITY.md.

Get started

What you need

  • Ubuntu 24.04 LTS. 2 vCPU, 4 GB RAM and 20 GB disk for a few hundred switches. Debian 12 is planned.
  • FreeRADIUS 3.2.10 is included. The release bundle carries a package built from the signed upstream release. The installer never overwrites an existing FreeRADIUS or /etc/freeradius.
  • Distribution packages only: PostgreSQL 16, nginx and Python 3.12 with its python3-* packages.
  • For EAP-TLS: a CA that issues client certificates, and a RADIUS server certificate.
  • Optional: Ubuntu Pro FIPS for FIPS mode.

About the bundled FreeRADIUS package

  1. Check the server

    A read-only check. It changes nothing.

    sudo ./deploy/preflight.sh

  2. Install

    Run the installer with no options and answer the questions: server name, management subnet, portal address, DNS resolvers, portal certificate and the first administrator.

    sudo ./deploy/install.sh
    Unattended install with an answers file

    Put the same answers in a file. The format is described in deploy/answers.sh.

    server_name: radius.example.net
admin_net: 192.0.2.0/24
switch_nets: "192.0.2.0/24 198.51.100.0/24"
listen_ip: 192.0.2.10
resolver: "192.0.2.53"
tls: self-signed
admin_username: netadmin
    sudo ./deploy/install.sh --answers site.yaml --print-answers   # check only
sudo ./deploy/install.sh --answers site.yaml

    The installer keeps your answers in /etc/radius-admin/site.yaml for later runs.

  3. Sign in

    Browse from the management subnet to https://<server name>/. Sign in with the one-time password the installer printed, choose your own password and set up two-factor authentication.

  4. Follow the setup checklist

    Add RADIUS clients, create access rules, set the switch-admin subnet and apply.

The full procedure, including migration from an existing FreeRADIUS server, is in the runbook. The README has the same steps next to the code.

Where it stands

radius-admin is a young project under active development. It grew out of a console that has run a production network, and is now being turned into something anyone can install. Expect rough edges and frequent improvements.

Current limitations

  • One distribution. The bundled FreeRADIUS package is built for Ubuntu 24.04 on amd64. Debian 12 follows.
  • One tested switch family. Cisco Catalyst 1200/1300 is what the project is tested against today. Vendor profiles are planned.
  • Certificates are yours to place. The installer expects the FreeRADIUS certificates under /etc/freeradius/certs/site/. Generating the whole FreeRADIUS configuration is the next phase.
  • Client-certificate MFA needs your PKI. The nginx phase expects the site CA bundle and an OCSP responder.
